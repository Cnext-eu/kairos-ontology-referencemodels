## EXAMPLE PROJECT: Kidslife IDP Solution

### Background Information

Kidslife is processing request from Belgian families for financial child support.
they receive many different documents (PDF, emails, letters, ....)

they inbound flow is using channels : 
email, letters (through scan and OCR using Kofax), mykidslife (self service portal), government document exchange. ....
They expect many document types to be processed, some documents are in fact a response to an outbound document generated by Kidslife using predefined templates which might have an barcode on it.

the envisioned solution should replace Kofax OCR and the document inbound flow should result in a summarization and classification of the document in a Zoho case ticket.
We also would like to use HITL (human in the loop) in case certain required fields in a document were not retrieved or found by the ai, allowing file managers of kidslife to manually review and add the missing required info using a purpose build ui.
Summarize the content of the inbound document to add as information field in the created Zoho ticket. scope of this solution is limited to create a new ticket in Zoho for inbound ticket, in a later phase inbound communication documents are added to existing zoho ticket as a continuation of an case (if it is a follow up conversation).
Kidslife distinguishes many document types in it's service delivery. Our solution will define document types, and potentionally sub types with a strict ontology of the fields to extract from the documents.

---------
We deliver this through Kairos platform, core edition.
The description of the platform and the constraints are mentioned in kairos-platform-v0.3.md


---------
important remarks:
the IDP solution will process Personally Identifiable Information (PII). The solution should be compliant to GDPR and legal consents by the users. This should fit in a broader legal framework managed by Kidslife. The IDP solution should also be compliant to EU AI Act. 


---------
IDP solution depends heavily in OCR and document extraction and enrichment capabilities.
we are still evaluation the best approach and we will refine this during the detailed solution design. 
For the HLSD, consider following and keep it abstract:
- use a framework optimized for document pre and post processing to manage document rotation, ...
we might consider azure content underdtanding, LLamaIndex or build ourselves using opensource langgraph + openCV
- leverage state of the art LLM or VLM for the OCR
- modular approach so we can swith VLM when better version is available.
- field extraction should include reference to the place of the document (location) so that it can be used to point or show to the user (groundness or visual inspection)  
- output should contain both MD style of the document and json structure output based on the ontology specs of the document type
- confidence score (if possible) to trigger human in the loop scenario in case validation is needed.
----------
